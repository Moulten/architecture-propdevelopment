# Требования к внешним интеграциям — Умный дом PropDevelopment

## 1. Контекст

В рамках развития продукта PropDevelopment внедряются две новые бизнес-функции для собственников жилья:

- **Интеллектуальный домофон** — открытие двери по распознаванию лица жильца или гостя по QR-коду
- **Интеллектуальный шлагбаум** — открытие въезда по распознаванию государственного номера автомобиля

Обе функции реализуются через интеграцию с **внешней платформой партнёра «Умный дом»** и требуют обработки чувствительных персональных данных: биометрии (изображения лиц) и данных о транспортных средствах (государственные номера). Дополнительно вводится **единый API Gateway** для всех партнёрских интеграций — это устраняет выявленную уязвимость (отсутствие централизованного контроля в текущем ландшафте).

## 2. Архитектурные изменения

### Новые компоненты

| Компонент | Тип | Описание |
|-----------|-----|----------|
| `smart-home-service` | Микросервис (Kotlin/SpringBoot) | Управляет бизнес-логикой умного дома: хранит списки авторизованных жильцов и номеров авто по каждому ЖК, обрабатывает запросы от мобильного приложения |
| `partner-api-gateway` | API Gateway | Единая точка входа для всех партнёрских интеграций. Обеспечивает аутентификацию, авторизацию, аудит и изоляцию данных между ЖК |
| `smart-home-db` | PostgreSQL | Хранит списки доступа (авторизованные лица и номера авто) в разрезе ЖК |

### Обновлённые компоненты

| Компонент | Изменение |
|-----------|-----------|
| `Витрина сервисов для собственников` (Mobile App) | Добавлен раздел «Умный дом»: управление списками доступа, статус устройств |
| `tenant-core-app` | Интеграция с `partner-api-gateway` теперь вместо прямого вызова ЖКХ-партнёров |

## 3. Требования к безопасности

### 3.1 Общие требования

| # | Требование | Обоснование |
|---|-----------|-------------|
| R-SEC-01 | Все соединения с партнёром используют **TLS 1.3**. Сертификаты с pinning на стороне мобильного приложения | Защита данных в транзите; критично для биометрии |
| R-SEC-02 | Биометрические данные (изображения лиц) **не хранятся** в инфраструктуре PropDevelopment. Хранятся только векторные embedding'и у партнёра | Соответствие 152-ФЗ: биометрия — специальная категория ПД |
| R-SEC-03 | Все запросы к API партнёра проходят через `partner-api-gateway`. Прямые соединения из бизнес-сервисов запрещены | Устранение уязвимости из задания: отсутствие централизованного контроля |
| R-SEC-04 | `partner-api-gateway` ведёт **аудит-лог** каждого запроса: timestamp, идентификатор запроса, ЖК, результат. Логи хранятся минимум 1 год | 152-ФЗ, ст. 19: журналирование обращений к ПД |
| R-SEC-05 | Данные о доступе строго изолированы по ЖК (**multi-tenancy**). Партнёр управляющей компании ЖК-1 не может получить данные ЖК-2 | Устранение уязвимости из задания: партнёр одной УК видит данные другой |
| R-SEC-06 | Применяется **rate limiting** на уровне `partner-api-gateway`: не более 100 запросов/мин на токен партнёра | Защита от перебора и DoS |
| R-SEC-07 | Данные о номерах авто (государственные номера) считаются **персональными данными** и обрабатываются с согласия собственника | 152-ФЗ, ст. 5: номер авто связан с ФИО владельца |
| R-SEC-08 | Согласие субъекта ПД на биометрическую обработку оформляется **отдельным подписанным документом** до активации функций умного дома | 152-ФЗ, ст. 11: биометрия требует письменного согласия |
| R-SEC-09 | Партнёр проходит **Security Assessment** перед заключением договора. Проверяется наличие сертификации ФСТЭК/ФСБ для обработки биометрии | Снижение рисков цепочки поставок |

### 3.2 Управление согласиями

```
Собственник → Мобильное приложение → [Запрос согласия на биометрию]
                                         ↓
                               [Подписание документа (ЭП или ручная подпись)]
                                         ↓
                               smart-home-service → [Запись согласия в smart-home-db]
                                         ↓
                               [Активация биометрии через partner-api-gateway]
```

## 4. Протоколы аутентификации и авторизации

### 4.1 Аутентификация собственника (Mobile App → PropDevelopment)

| Параметр | Значение |
|----------|---------|
| Протокол | OAuth 2.0 + OpenID Connect |
| Identity Provider | `auth-service-2` (Keycloak) |
| Flow | Authorization Code с PKCE (для мобильных приложений) |
| Токены | Access Token (15 мин) + Refresh Token (30 дней) |
| MFA | Обязательная при активации функций умного дома |

### 4.2 Авторизация запросов к smart-home-service

| Параметр | Значение |
|----------|---------|
| Механизм | JWT Bearer Token (из Keycloak) |
| Проверка прав | RBAC: роль `owner` + атрибут `jk_id` (ЖК) совпадает с запрашиваемым ЖК |
| Scope | `smart-home:read`, `smart-home:write` |

### 4.3 Аутентификация PropDevelopment → партнёр (через partner-api-gateway)

| Параметр | Значение |
|----------|---------|
| Протокол | OAuth 2.0, Client Credentials Flow |
| Client Secret | Ротация ежеквартально, хранится в Kubernetes Secret / Vault |
| Область токена (scope) | `devices:intercom:manage`, `devices:barrier:manage` |
| Привязка к ЖК | `jk_id` передаётся как обязательный claim в каждом запросе |

### 4.4 Авторизация партнёра → PropDevelopment (callback/webhook)

| Параметр | Значение |
|----------|---------|
| Механизм | Webhook с подписью HMAC-SHA256 |
| Ключ подписи | Уникальный per-partner, ротация раз в квартал |
| Проверка | `partner-api-gateway` проверяет подпись до передачи запроса в `smart-home-service` |

## 5. Организация взаимодействия между системами

### 5.1 Архитектурная схема потоков

```
[Собственник]
     │
     │ HTTPS, OAuth 2.0/PKCE
     ▼
[Mobile App: Витрина сервисов]
     │
     │ REST, JWT Bearer
     ▼
[auth-service-2 / Keycloak] ──── проверка токена
     │
     │ REST, JWT Bearer
     ▼
[smart-home-service]
     │     │
     │     │ JDBC
     │     ▼
     │  [smart-home-db]
     │  (списки доступа по ЖК)
     │
     │ REST (внутренний)
     ▼
[partner-api-gateway]  ◄──────── [Все остальные партнёры: ЖКХ, Платёжная система]
     │
     │ REST, HTTPS, TLS 1.3
     │ OAuth 2.0 Client Credentials
     │ Header: X-JK-ID, X-Request-ID
     ▼
[Партнёр «Умный дом»]
     ├──► [API: Умный домофон] — распознавание лиц, открытие
     └──► [API: Умный шлагбаум] — распознавание номеров, открытие
```

### 5.2 Ключевые сценарии взаимодействия

#### Сценарий A: Добавление жильца в систему домофона

1. Собственник в Mobile App → «Добавить жильца» → вводит ФИО, загружает фото
2. Mobile App → `smart-home-service`: `POST /api/v1/jk/{jk_id}/residents` (JWT)
3. `smart-home-service` проверяет: токен действителен, `jk_id` в токене совпадает с path param
4. `smart-home-service` → `partner-api-gateway`: `POST /partner/smart-home/residents` (OAuth CC)
5. `partner-api-gateway`: добавляет заголовки X-JK-ID, X-Correlation-ID, пишет в аудит-лог
6. Платформа партнёра: создаёт биометрический профиль, возвращает `resident_id`
7. `smart-home-service` → `smart-home-db`: сохраняет `resident_id` (без фото/биометрии)
8. Mobile App: подтверждение пользователю

#### Сценарий B: Регистрация автомобиля для шлагбаума

1. Собственник в Mobile App → «Добавить автомобиль» → вводит гос. номер
2. Mobile App → `smart-home-service`: `POST /api/v1/jk/{jk_id}/vehicles`
3. `smart-home-service` → `partner-api-gateway` → партнёр: регистрация номера в базе шлагбаума
4. `smart-home-service` → `smart-home-db`: хранит зашифрованный гос. номер

#### Сценарий C: Физическое открытие шлагбаума

1. Камера шлагбаума: распознаёт номер авто
2. Устройство партнёра → платформа партнёра: поиск номера в базе
3. Если авторизован → открытие шлагбаума (offline, без запроса в PropDevelopment)
4. Платформа партнёра → `partner-api-gateway` (webhook): `POST /webhooks/barrier/events`
5. `partner-api-gateway`: проверяет HMAC подпись → `smart-home-service` → аудит-лог события

### 5.3 API-контракт: partner-api-gateway ↔ Партнёр «Умный дом»

| Метод | Endpoint | Описание |
|-------|----------|----------|
| POST | `/partner/smart-home/residents` | Добавить жильца (биометрический профиль) |
| DELETE | `/partner/smart-home/residents/{id}` | Удалить жильца (право на забвение) |
| POST | `/partner/smart-home/vehicles` | Добавить автомобиль |
| DELETE | `/partner/smart-home/vehicles/{plate}` | Удалить автомобиль |
| GET | `/partner/smart-home/devices/{jk_id}/status` | Статус устройств ЖК |

**Обязательные заголовки в каждом запросе:**
```
Authorization: Bearer <access_token>
X-JK-ID: <идентификатор_ЖК>
X-Request-ID: <UUID_запроса>
Content-Type: application/json
```

### 5.4 Изоляция данных по ЖК

Каждый запрос к партнёру содержит `X-JK-ID`. Партнёр обязан по договору:
- Хранить данные каждого ЖК в изолированных пространствах
- Не допускать перекрёстного доступа между ЖК
- Предоставлять API для полного удаления данных конкретного ЖК

## 6. Требования к SLA и надёжности

| Параметр | Требование |
|----------|-----------|
| Доступность `partner-api-gateway` | ≥ 99.9% (≤ 8.7 ч простоя в год) |
| Latency (открытие домофона/шлагбаума) | P95 ≤ 3 сек (устройство работает offline, webhook — фоновый) |
| Timeout запроса к партнёру | 5 сек; при таймауте — graceful degradation (логирование, без ошибки в UI) |
| Retry policy | Exponential backoff, 3 попытки, jitter |
| Circuit breaker | При >30% ошибок за 60 сек — отключение с алертом |

## 7. Требования к договору с партнёром

| # | Требование |
|---|-----------|
| C-01 | Партнёр является **оператором персональных данных** в части биометрии и несёт самостоятельную ответственность по 152-ФЗ |
| C-02 | Партнёр обязуется пройти аттестацию ФСТЭК для систем, обрабатывающих биометрические ПД |
| C-03 | Партнёр предоставляет API для **удаления всех данных субъекта** (право на забвение, ст. 21 152-ФЗ) не позднее чем через 72 часа после запроса |
| C-04 | Данные PropDevelopment не используются партнёром для обучения моделей или в целях третьих сторон |
| C-05 | Партнёр уведомляет PropDevelopment об инцидентах ИБ в течение **24 часов** |
| C-06 | Ежегодный совместный аудит безопасности интеграционного слоя |

## 8. Матрица рисков новых интеграций

| Риск | Вероятность | Влияние | Митигация |
|------|------------|---------|-----------|
| Утечка биометрических данных у партнёра | Средняя | Критическое | Биометрия хранится только у партнёра; PropDevelopment хранит только ID профиля |
| Несанкционированный доступ к данным другого ЖК | Средняя | Критическое | Обязательный `X-JK-ID` + проверка на уровне gateway + условие в договоре |
| Недоступность платформы партнёра | Средняя | Высокое | Устройства работают offline; webhook — асинхронный; circuit breaker на gateway |
| Использование биометрии без согласия субъекта | Низкая | Критическое | Активация только после подписания согласия; хранение факта согласия в smart-home-db |
| Подмена webhook от партнёра (spoofing) | Низкая | Среднее | HMAC-SHA256 подпись; проверка IP по allowlist |
