# Проверочный лист безопасности бизнес-систем PropDevelopment

---

## Обоснование выбора разделов

Разделы проверочного листа выбраны исходя из четырёх задокументированных проблем и бизнес-приоритетов компании. Ниже — обоснование каждого раздела.

### Раздел 1 — Управление доступом и аутентификация
**Почему включён:** Зафиксирован действующий инцидент: клиенты видят в личном кабинете данные других клиентов. Это прямое следствие либо нарушения изоляции сессий, либо ошибки авторизации на уровне ресурсов. Раздел является приоритетом № 1 для аудита.

### Раздел 2 — Защита персональных данных (152-ФЗ)
**Почему включён:** Бизнес-требование — проверить соответствие законодательству РФ. Компания обрабатывает ФИО, телефоны, email, данные онлайн-сделок и платежей ЖКУ. Несоответствие 152-ФЗ влечёт штрафы и репутационные риски. API партнёров уже выявлено как источник избыточной передачи ПД.

### Раздел 3 — Безопасность API и внешних интеграций
**Почему включён:** Явно описанная системная проблема: «нет единых политик по безопасности» для API партнёров-поставщиков ЖКУ. Партнёр из одной управляющей компании может просматривать и изменять данные клиентов другой. Компания планирует расширять партнёрские интеграции — без закрытия этой проблемы масштабирование увеличит риски.

### Раздел 4 — Управление потоками данных
**Почему включён:** Две зафиксированные проблемы: (а) нет координации между несколькими точками регистрации клиентов, (б) нет технических ограничений на доступ к хранилищу данных (Greenplum/S3). Это блокирует развитие BI/ML/AI-направления и создаёт риски утечки через аналитические системы.

### Раздел 5 — Мониторинг, логирование и реагирование на инциденты
**Почему включён:** У компании один специалист по ИБ, и ему не передаются все изменения — процесс реагирования на инциденты де-факто сломан. Утечка у конкурента заставляет руководство оценить готовность к подобным сценариям. Без централизованного мониторинга невозможно своевременно выявлять атаки.

### Раздел 6 — Управление уязвимостями и безопасность инфраструктуры
**Почему включён:** Большинство сервисов развёрнуто в Kubernetes. Без сетевого разграничения подов и управления секретами даже одна скомпрометированная служба может дать доступ ко всем остальным. Раздел важен в контексте гибридной инфраструктуры (собственный ЦОД + облако).

## Условные обозначения

| Статус | Описание |
|---|---|
| ✅ | Выполнено — наличие подтверждено |
| ❌ | Не выполнено — нарушение зафиксировано |
| ⚠️ | Частично выполнено — реализовано с недостатками |
| ❓ | Требует проверки — данных недостаточно |

| Критичность | Описание |
|---|---|
| 🔴 Критический | Немедленное устранение; прямой риск утечки ПД или остановки бизнеса |
| 🟡 Значительный | Устранение в плановом порядке; существенный риск |
| 🟢 Незначительный | Рекомендация; минимальный риск |
